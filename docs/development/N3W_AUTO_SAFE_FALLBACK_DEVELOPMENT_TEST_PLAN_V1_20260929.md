## 1. 决策摘要

**推荐暂缓完整 B2，先实现“保留原身份，通过 auto 重新寻找连接地址”的小范围修补。**

这里的“回退”是：T1 地址变了，节点原来保存的 Broker 地址失效，但 T1 的动态发现服务仍可访问；节点重新取得一个候选地址，使用原有证书信任和原有账号验证，成功后继续上报。

它不是清空配对资料，也不是恢复出厂设置。若 auto 发现本身不可用，节点不能凭空得到新地址，应保持本地采集、可用 Relay 和有限重试，并给出清楚的离线原因。

第一版采取以下约束来控制规模：

1. 复用现有 UDP 发现报文，不新增配对协议，不调用 hello、begin、身份修复或重新注册。
2. 只适用于 **Manager 与 Broker 同在一台 T1、Broker 端口已由原可信配置给定** 的部署。
3. 新地址仅保存在内存中。原来的长期连接配置、身份和密钥不改写。
4. 证书信任根、校验名称、节点专属账号保持原值；不接受发现报文下发的新凭据。
5. 复用已有 Direct/Relay 恢复调度，不另建一套抢占无线的循环。
6. 首先验证运行中的 MQTT 客户端确实能安全切换地址；这一步不成立，就暂停扩大开发。

第一版的代价也必须接受：**设备断电后会忘记内存中的新 IP，下一次启动可能要重新发现。** 这是省去永久配置迁移和写入恢复逻辑的明确取舍。

## 2. 与 B1、B2、B3 的关系

| 项目 | 本方案如何处理 |
|---|---|
| B1：T1 Broker 绑定旧 LAN IP 导致服务启动失败 | 依赖已经完成的部署修补；本方案不能恢复一个未启动的 Broker |
| KF-098：配对发现返回旧地址 | 复用已修补的 `GH_N3W_PAIRING_ADVERTISED_HOST=auto`；不重新打开已关闭故障 |
| B2：稳定名称、自动发布、证书生命周期 | 暂缓；本方案不新增 mDNS、局域网 DNS 或自动续期系统 |
| B3：已配对节点仍使用旧 Broker IP | 覆盖“原身份及凭据有效、同机服务、可重新发现”的运行时恢复子集 |
| Board B 当前身份恢复 | 独立处理；不能靠本方案绕过 `repair_intent_required`，不能把未完成配对的 B 当作本方案正常样本 |
| 旧地址永久迁移 | 第一版不做；因此不能把整个 B3 宣称为已关闭 |

与 V0.7 路线及全系统简化规划保持一致：统一生产固件、用户不填固定 IP、网络故障不导致自动退役、本地采集不依赖主机在线、不新增应用层补发体系。

### 3.2 底层风险的证据等级

已恢复的 ESPHome 后端参考源码中，`set_server()` 只赋值 host/port；`connect()` 仅在尚未初始化时创建和启动底层客户端。由此可判断：**只改上层地址再 connect，不能作为运行中换址的可靠实现。**

这份参考源码不冒充即将构建产物的权威来源。实施阶段必须重新从冻结工具链取得实际生成的 MQTT 源码、ESP-IDF/ESP-MQTT 版本及文件摘要，确认已有项目补丁全部生效后，再选择适配方法。

ESP-MQTT 官方接口提供配置更新能力，也明确限制在 MQTT 事件回调中执行 stop/destroy 等操作。该能力仅证明存在可评估入口，不证明当前 ESPHome 包装层已经正确支持换址或有界退出。[官方 ESP-MQTT 文档](https://docs.espressif.com/projects/esp-idf/en/v5.4/esp32/api-reference/protocols/mqtt.html)

### 3.3 实施前仍需核实

- A/B/C 实际固件、有效配对状态、存储结构、凭据代次；不从旧聊天记录推定。
- T1 当前 Manager/Broker 是否同机，Broker 原端口是否可从节点访问。
- 原 CA 与 TLS 校验名称能否在新 IP 上验证同一个 Broker；证书是否有效、时间是否可信。
- 实际后端错误回调能区分到什么粒度；不能按一个 disconnected 布尔值猜故障原因。
- 取消正在进行的 TCP/TLS 连接是否能在原恢复窗口内真正释放资源。

## 4. 支持范围与不支持范围

### 4.1 可以自动恢复的典型情况

- 同一 T1 DHCP 地址改变，Broker 身份及节点账号未变。
- T1 重启后得到新地址，服务稍后恢复，节点持续有限重试后恢复上报。
- 节点与 T1 移到新局域网，节点已经完成新 Wi-Fi 联网，发现广播可达，原信任仍有效。
- 同一启动周期内 T1 多次换地址；每次都重新验证，不能永久记住第一个候选。

### 4.2 不能承诺自动解决的情况

| 情况 | 正确处理 |
|---|---|
| Wi-Fi 密码或网络名称变化，节点无法联网 | 使用已有重新配网流程；不清配对身份 |
| 广播被隔离、T1 跨不支持的网段、auto 服务关闭 | 保持离线/Relay，提示发现不可用；恢复网络条件后重试 |
| Broker 与 Manager 分开部署或端口改变 | 本版禁止从 Manager 地址推导 Broker 地址；另走可信配置更新 |
| 证书过期、错误 CA、TLS 校验名称不匹配、时间未就绪 | 拒绝连接；记录分类；不能关校验 |
| 节点账号撤销、身份缺失、配置损坏、尚未完成配对 | 保持现有身份/修复边界；独立处理 |
| T1 丢失原 CA 私钥、账号数据库或系统身份 | 地址恢复无效，需备份恢复或独立身份迁移 |
| 新旧两台 T1 克隆了相同私钥、证书和账号 | 本方案无法辨别合法克隆与原机；不宣称解决此问题 |

特别说明：原证书含旧 IP 并不自动证明本方案不可能。若原 TLS 校验标识仍与证书匹配，且后端允许把连接 IP 与校验标识分离，可能仍能连接；必须在实际后端测试。相反，只修改 IP 不会修复真正的证书校验失败。

## 5. 配置处理规则

| 数据 | 第一版处理 |
|---|---|
| 持久 `broker_host` | 只读保留，作为启动初始目标和故障回退依据 |
| 内存候选 IP | 本轮发现获得，未经 TLS/MQTT 验证前不得标成可信 |
| 内存已验证 IP | 成功后作为本次启动后续重连的优先地址 |
| Broker 端口 | 永远使用原可信配置；不使用发现回应中的 Manager HTTP 端口 |
| CA、TLS 校验名称 | 不变；发现回应无权覆盖 |
| MQTT 用户名、密码、client_id、凭据代次 | 不变 |
| system_id、node_id、peer trust、ESP-NOW 密钥 | 不变 |
| Wi-Fi、传感器、电源和显示配置 | 不变 |
| 配对状态、待确认配对记录、退役标记 | 本恢复功能不写、不清、不绕过 |

“清空失效配置”限定为：关闭已失败的临时连接、丢弃过期候选、撤销内存覆盖地址。不得调用整库 erase、恢复出厂、清空 `gh_n3w_v2` 或重新发放凭据。

原 Broker 记录和 peer 记录不完整或身份不一致时，按现有检查拒绝启动恢复；不通过发现填补丢失身份。

## 6. 恢复流程与状态转换

### 6.1 触发条件

同时满足以下条件才能进入恢复：

1. 已配对且本地身份/凭据记录有效，未处于退役、身份修复或首次配对中。
2. 当前 Wi-Fi 已联网且有有效 IPv4。
3. 部署合同允许“Manager 地址作为同机 Broker 候选”。
4. MQTT 持续失败达到门槛，而非一次丢包。
5. 现有 Direct 恢复调度允许本轮尝试，且剩余时间足够安全退出。

初始建议门槛：Wi-Fi 连续可用期间 MQTT 至少 10 秒未恢复，且观察到两个不同连接尝试的可归类失败；或者一次连接尝试已到达它自己的明确超时。没有回调的黑洞连接也必须能触发有限恢复。这里是**建议待测参数**，不是现有代码事实。

统计以连接尝试编号去重，不能把一个失败的多个回调算成多次失败。Wi-Fi 丢失不累计成地址故障；网络重新建立后按现有调度开始新窗口。

### 6.2 状态与退出规则

| 状态 | 执行动作 | 正常出口 | 失败或取消出口 |
|---|---|---|---|
| 正常/等待 | 使用内存已验证地址，否则原地址；维持既有重连 | 满足触发条件后进入发现 | Wi-Fi 不可用则等待，不清配置 |
| 发现 | 发一个带新随机关联值的查询，收集筛选回应 | 得到候选进入准备换址 | 到期、无回应、网络变化：退避 |
| 准备换址 | 暂停旧自动重连与发送入口，确认旧连接和回调退出 | 把候选交给唯一 MQTT 后端 | 退出未确认：拒绝新连接，报告失败 |
| 验证候选 | 原 CA/名称完成 TLS；再发送原 MQTT 登录资料 | TLS 与登录均成功，标记内存地址已验证 | 拒绝该候选；如本轮有余量可试下一项 |
| 恢复 Direct | 沿用原 Direct 确认及无线交还流程 | 路径提交成功，恢复业务 | 超时走原 Relay 恢复流程 |
| 退避/待处理 | 保存分类结果及下次允许时间 | 到时继续尝试或既有路径恢复 | 绝不自动重新配对或反复重启 |

不新增一个永久“锁死”状态：某候选证书错误只能拒绝该候选，不能让局域网里一个伪造回应永久禁用正确 T1 的恢复。

### 6.3 错误分类及动作

| 观测 | 允许做什么 | 禁止推断或动作 |
|---|---|---|
| 无 Wi-Fi、无 IPv4 | 等网络；有 Relay 则按原流程工作 | 不能清 Broker 配置 |
| TCP 拒绝/超时/目标不可达 | 允许重新发现和换候选 | 不宣称已证明 T1 换地址 |
| 旧 IP 上出现错误证书 | 拒绝该连接；允许有限发现其他候选 | 不能直接把全局状态锁为证书损坏，旧 IP 可能已给了别的设备 |
| 新候选错误 CA/名称/日期 | 拒绝该候选，不发送 MQTT 登录资料；可继续筛选 | 不能信任回应自报的 system_id 或新证书 |
| 已通过 TLS 的 Broker 拒绝账号 | 本轮终止换址，进入账号待处理与慢速复查 | 不能把撤销当成地址问题，无限换机或重配 |
| TLS 通过、MQTT 在线但无业务前进 | 独立报告业务未恢复，检查发布/权限/Manager | 不能仅因 MQTT connected 宣告验收成功 |
| 错误来源不明确 | 记为未知；允许受限发现，保留原信任 | 不能伪造为网络错误或跳过安全检查 |
| auto 解析失败/无回应 | 保持原身份、退避 | 不能复用未验证旧回应或恢复出厂 |

证书有效期和时间校验必须保留。没有公网但当前产品缺少可用时间来源时，应标成明确适用限制/前置阻塞，不在本方案里悄悄扩展为新的可信时间系统。

## 7. 发现协议与候选筛选

### 7.1 复用的部分

继续发送 `gh.discovery.query/1`，包含现有协议支持列表、hardware_id、全新 request_id 和 nonce；继续接收 `gh.discovery.response/1`。不在发现包中发送密码、Setup Secret、CA 私钥或节点密钥。

新入口只返回候选地址及必要诊断信息，不调用 `SimplePairingClient::run_once()`，不走 HTTP `/v2/pairing`。保持原首次配对路径的报文语义，相关解析代码若共用，必须回归 KF-099。

### 7.2 候选必须全部满足

- 报文大小有上限，JSON 结构、schema、协议及字段类型符合现有合同；超大或截断报文拒绝。
- request_id、nonce 对应本轮；随机生成失败则本轮不发查询。
- system_id 等于已保存系统，作为降低误选的初筛；它不是认证。
- host 是有效的本地单播 IPv4；拒绝空值、`auto`、主机名、回环、组播、广播、未指定地址、板自身地址及不受支持范围。
- 第一版限定同一子网直达发现；用当前板端地址与掩码验证，不简单把所有私有 IP 都当作可接受目标。
- 用 `recvfrom` 记录来源；第一版要求来源 IP 与 advertised host 相符。若多网卡现场不满足，明确判为不支持，不放宽为任意转向地址。
- ttl_s 合法，候选使用寿命不超过服务声明与本地上限中较小者；nonce、时间和来源都不等于密码学认证。
- 不从候选 port 推导 Broker 端口；Manager 的 HTTP 地址只提供同机 IP 线索。

上述同子网和来源一致性是 V1 范围收窄，需在 T1 多网卡及路由选择实测中验证；不满足时不能用关闭筛选来赶进度。

### 7.3 有界接收和多主机

建议每轮一次查询，接收窗口不超过 1 秒；每次主循环最多处理固定数量报文，累计最多解析 8 个、保留最多 3 个去重候选。单轮最多试 2 个地址，始终受总时限限制。参数在阶段 0/1 固定。

不能“第一个回应就是正确 T1”。错误系统回应直接跳过；同系统伪造回应仍必须接受原 TLS 验证。优先保留已验证地址，其他候选采用稳定排序并对失败项短期冷却；各轮轮换未尝试候选，避免每次只试同一个坏地址。

发现结果的 TTL 只约束**尚未验证的线索**。TLS/MQTT 已验证并在线的连接不因 30 秒发现 TTL 到期而断开。内存已验证地址在本次启动内可优先复用；它失败后重新发现。

UDP 可伪造，攻击者仍可能通过淹没回应妨碍可用性；本方案提供有界资源和认证保护，不承诺在主动干扰网络中必定恢复。不得为此在 V1 新增一整套发现签名体系。

## 8. MQTT 换址与并发约束

### 8.1 单一连接所有者

整个节点仍只运行一个业务 MQTT 客户端，不为每个候选创建长期并行客户端。换址由组件/任务协调，在回调外执行需要等待的操作；回调只提交小型事件，不直接销毁客户端或递归开始新连接。

建议适配接口语义为：开始候选连接、查询状态、请求取消、确认退出、提交内存目标。接口名称在源码阶段决定，不在本规划里制造第二套产品框架。

每轮使用递增的内存尝试编号和当前网络代次：

- 旧连接的成功、断开、错误或发布完成回调，不能提交新轮结果。
- Wi-Fi 丢失/地址变化、上层取消、Radio ownership 改变时，候选立即失效。
- 只有确认旧底层连接和事件来源停止后才启用新目标。
- 已收到“取消”并不等于底层已停止；需要实际可证的终态。
- 销毁期间保持 host、CA、校验名称和凭据内存有效，避免悬空指针。
- 栈内配置更新必须保留 CA、校验名称、账号、client_id、LWT、keepalive、会话及订阅设置。
- 自动重连不能在换址过程中偷偷继续连接旧 IP；恢复后自动重连优先使用本次启动的已验证目标。

### 8.2 实现方法的优先顺序

1. 在冻结版本上验证“停止并确认退出 → 完整更新配置 → 重启同一客户端”的接口；若可控，优先使用。
2. 若包装层或底层不能可靠更新，评估“有界停止 → 释放并清理旧事件 → 用完整原信任配置重建”。
3. 两种方式都不能保证有界退出，就关闭此候选能力并停止发布；不以延长健康 Relay 预算或重启整板来掩盖。

优先沿用仓库现有版本绑定适配方式，禁止手改 `.esphome/build` 生成物作为唯一实现。若新增/重构模块，先遵循 `docs/development/module-lifecycle-rules.md`，给出模块入口、责任、测试和最终生产编译目标。

### 8.3 遥测和队列

维持已接受的 Option B：未获得真实传输机会的数据可进入既有有界队列；已经提交后失败的数据按既有规则处理，不增加应用层自动重发，不承诺每条五秒数据都不丢。

换址期间必须明确谁拥有每条待发数据，旧 MQTT outbox/异步发送任务如何停止，QoS 状态如何处理。不得同时由旧连接、新连接和 Relay 重复接管同一条业务样本。底层 QoS 重投递仍由现有 Manager 去重规则处理，不当作新功能。

## 9. 时限、退避与无线调度

### 9.1 不变的硬边界

| 场景/阶段 | 原有边界 | 本方案要求 |
|---|---:|---|
| 健康 Relay 下整轮 Direct 探测 | 30 秒 | 包含 Wi-Fi、发现、换址、TLS/MQTT、确认；不得重置计时 |
| 无可用 Relay 的整轮恢复 | 120 秒 | 不扩大；Wi-Fi 阶段最多 85 秒 |
| MQTT 阶段 | 25 秒 | 发现、候选连接及清理占用该阶段，不额外加 25 秒 |
| Direct 确认阶段 | 5 秒 | 沿用既有确认规则；预算不足则失败退出 |
| 恢复退避 | 现有 60→120→240→480 秒路径 | 复用，不新增快速广播循环 |

第一版建议在 MQTT 可用时间内，为发现预留最多 1 秒，单个候选 TCP/TLS/MQTT 尝试最多 6 秒，正常取消清理预留至少 2 秒；确认窗口使用原规则。有效截止时间取“父级绝对截止、MQTT 阶段截止、候选上限”中最早者，并提前留出退出余量。

这些子预算必须通过底层实测确认，不得把“线程中等待”当成有界，也不能把耗时丢到后台就声称没有占用无线。资源未释放时不重新发起下一轮。

### 9.2 健康 Relay 场景

发现 UDP 只能在已获准、已建立 Wi-Fi 的 Direct 探测里执行；Relay 稳态时不自行连接 AP、不主动切信道、不绕过 unicast drain 和 teardown。

新地址成功只是 MQTT 条件之一，仍走现有 Direct 路径确认、无线提交和数据归属检查。失败走原 Relay 恢复入口；不新增第二个 Direct/Relay 状态机。

### 9.3 服务长期不可用

每次允许的恢复窗口最多一轮广播。没有候选或连接失败后进入既有退避；全局还设置每节点不少于 60 秒的广播间隔下限，使用调度允许范围内的小幅随机错峰，避免多板同时轰击 T1。网络重连和报文洪泛不得不断重置下限。

已有已验证地址在线时不广播、不轮询其他 T1、不主动迁回旧地址。恢复后若再次失效，才重新启动同样的有限流程。

### 9.4 恢复时间怎么衡量

30 秒是一次健康 Relay 探测的占用上限，**不是从 T1 换 IP 到恢复业务的总时限**。总时长还包含尚未到期的现有退避。

测试同时记录：地址变化时刻、Wi-Fi 就绪时刻、下次允许探测时刻、发现开始、TLS 成功、MQTT 成功、Direct 提交、Manager 第一条新数据及后续两次前进。

建议正常受控样本从服务和网络可用起：

- 无 Relay、调度未积累长退避的首次恢复目标不超过 180 秒。
- 已进入最长退避的样本，单次成功条件下验收窗口按 `480 秒等待 + 120 秒尝试 + 30 秒业务确认余量 = 630 秒` 预留。
- 630 秒是本规划的测试窗口，不是当前产品保证；连续服务失败不应被判成“超过窗口就清配置”。

## 14. 实机执行设计

### 14.1 样本选择

先选“身份和业务均正常”的一块已配对板，不固定猜测 A/B/C 谁可用。Board B 若仍处于身份修复等待，先排除出首轮；该状态不算地址恢复失败。后续 B 在身份恢复并验证后可加入同一矩阵。

### 14.2 第一次单板测试

1. 精确核对候选源提交、生产/夹具产物摘要、板硬件身份、分区与 NVS 保留策略。已有授权不明时不写板。
2. 经独立授权升级固件，仅改批准的应用分区/升级入口；不擦 NVS、不生成新身份。
3. 稳定供电，建立 90 秒 Direct 基线，记录原 node_id、boot、序号、来源和 Manager 状态。
4. 在隔离网络中先预演 T1 换址和回滚；真实现场换址必须有目标接口、恢复管理通道和明确授权。
5. 执行 T1 地址变化，保持板供电；该轮不插 USB、不重启板、不人工改节点地址。若需移动板，先等待明确 MOVE 提示；无人交互脚本用倒计时。
6. 观察恢复时间线。第一条经 Direct 到达 Manager 的新数据后，至少再看到两次序号/更新时间前进，原 boot 与节点身份一致。
7. 随后进行 600 秒稳态观察，记录缺失、重复、最长业务间隔、重启和错误分类。
8. 重复地址变换至少三轮，包含旧 IP 被其他服务占用的一轮；每轮独立判定。

90 秒和 600 秒是基线及稳态观察窗口，不能偷换成所有恢复情形必须在 90/600 秒内完成。最长退避样本的转换窗口单独按第 9 节设置。

### 14.3 多板与 Relay 测试

- 一块 Direct 网关和一块 Relay Child：改变 T1 地址，验证网关自行恢复后 Child 仍归属原实体。
- A/B 互换网关角色重复；同一轮标明允许移动的板，其他板不动。
- A/B 均可 Direct、C 在 Relay：验证选择与滞回不变；不增加动态负载均衡。
- 所有网关上游同时失效：允许业务暂时离线，本地功能保持；不将“有 Relay 链路”误报为端到端正常。
- 加入第二台不同身份 T1：错误系统不接收账号，正确系统能被找到。
- 最后单独做断电重启测试，不能把这一轮与同 boot 迁移结果混算。

### 14.4 失败停止条件

出现身份/凭据变化、向错误证书服务发送登录资料、NVS 被清写、看门狗或重启风暴、无线退出超时、异常重复实体、不可解释任务/内存增长时，立即停止扩大测试并保存最小证据。不能靠不断重启、刷新凭据或重新配对把失败掩盖掉。

## 15. 验收证据与诊断设计

至少记录以下脱敏字段：

| 组别 | 必需信息 |
|---|---|
| 版本 | source SHA/tree、依赖锁定信息、构建配置摘要、固件 SHA256、production/harness 区分 |
| 目标 | Board 身份的受控绑定、system/node 是否一致、凭据代次是否不变、boot 是否同一 |
| 恢复 | 触发原因、尝试编号、网络代次、当前阶段、剩余时间、候选数、拒绝分类、下一次允许时间 |
| 网络 | 旧/新目标的脱敏标记、发现是否收到、实际连接是否到新目标、TLS/MQTT 分别通过与否 |
| 业务 | Manager 接纳的来源、boot、seq、更新时间，第一条后至少两次前进，HA 实体无变化 |
| 系统 | MQTT client/task/socket 数、堆趋势、主循环最大耗时、采样和显示周期、异常复位 |
| T1 | 服务状态和容器身份；区分计划内换网/重启与意外 Manager 重启 |

不打印密码、Setup Secret、密钥或完整凭据包；公开归档不放原始抓包和敏感网络信息。必要的私有证据保存摘要、大小、时间、目的和板关联。

“没有某条日志”只能记为证据不足；应优先使用实际连接目标、服务端拒绝记录、Manager 接纳数据及持久状态前后对比。

设备内没有新增 Manager 应用 ACK 的情况下，固件可以报告 TLS/MQTT 成功和本地路径提交，不能声称自己已经证明 Manager 接纳。完整业务成功由验收观察端确认，不为此新增 ACK 协议。

## 16. 升级、回滚和运维

### 16.1 旧节点升级

当前源码没有本方案入口，因此旧固件不会因为 T1 开启 auto 就获得这项能力。A/B/C 是否已搭载其他等价实现，要按实际源码/产物核对；否则需一次保留 NVS 的受控升级。

已经无法连接旧 IP 的节点，也可能无法依靠原 MQTT 路径升级。优先检查已有独立本地升级入口；不存在时使用受控 USB/应用分区刷写。不能为了升级方便先清身份。

### 16.2 回滚分两层

- **运行时失败**：丢弃未验证候选，保留原持久地址与最后已验证内存地址；到下个批准窗口再试。不能为恢复旧变量破坏仍健康的连接。
- **固件回滚**：回到上一批准版本，NVS 格式不变。旧版本可能再次卡在旧 IP，因此“可回滚固件”不等于“业务一定恢复”；需提前准备测试网络恢复旧地址，或已有受控配置维护方案。

回滚包需绑定源、产物、目标、分区和有效授权。若试验中改变 T1 LAN，必须有恢复管理访问的办法；不把恢复出厂作为自动后备措施。

### 16.3 面向用户的状态

尽量复用现有诊断/显示，不新增完整设置页面。建议短句：

- “正在重新寻找主机”
- “未找到主机，本地监测继续”
- “主机身份验证失败”
- “设备授权需处理”
- “连接已恢复”

“连接已恢复”的设备端显示只表示本地已确认连接；运维验收仍以 Manager 数据为准。普通用户不需要输入 IP、证书或端口。

## 17. 工作量与缩减策略

相比完整 B2，本方案省去了稳定名称发布、mDNS 解析、自动证书续期、全量首次初始化、名称冲突治理和永久地址迁移。但 MQTT 生命周期与单射频安全边界仍必须验证，不能承诺只改几行代码。

以下是规划估算，不是已测工时或日历承诺：

| 工作 | 有效工程日粗估 |
|---|---:|
| G0 前提核对与 G1 最小换址验证 | 0.5～1 |
| G2 有界发现、内存地址与恢复接入 | 1～2 |
| G3 聚焦/集成测试、编译与复核 | 1～1.5 |
| G4/G5 现场操作、问题处理与收口 | 0.5～1.5 |
| 合计 | 约 3～6 |

不包含排队、现场准备及 24 小时长稳等待；开发自动化程度与缺陷数量会改变工时。**先把 G0/G1 控制为半天至一天的可行性门。** 若出现需要深改 MQTT 后端、另做可信时间系统、引入可信 Broker 更新协议或长期存储迁移的证据，先给出缩减/延期选项并重新估算，不沿用 3～6 天承诺继续扩大。

发布必需项就是本文件 48 项；不把跨网段 DNS、证书轮换和完整 B2 的测试一起塞回来。可并行的是不冲突的测试准备和文档；恢复接口未冻结前不拆成多条互相猜接口的源码线。
