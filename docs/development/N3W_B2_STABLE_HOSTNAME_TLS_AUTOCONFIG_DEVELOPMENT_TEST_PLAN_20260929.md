## 1. 目标与完成后的用户体验

B2 要使同型号节点使用同一份生产固件。用户给 T1 和节点联网，扫描或确认目标设备，点击加入；系统自动完成稳定名称分配、证书准备、可信配置下发和首次连接。用户不输入 IP、端口、系统内部编号或证书，也不需要为了正常部署设置路由器的固定地址。

在支持的局域网中，T1 的 DHCP 地址变化后，已经采用 B2 配置的节点应重新找到原 Broker，验证其身份并恢复上报。节点名称、归属、Home Assistant 实体及历史数据不因此改变。

不能把目标扩大解释为：

- 任意访客网络、跨网段、禁止组播或客户端隔离的网络都自动可用。
- Wi-Fi 名称和密码改变后，节点无需重新获得网络配置。
- 没有有效备份，更换 T1 就能冒充旧系统接管节点。
- 发布一个 .local 名称，已有节点中的旧数字 IP 就自动消失。
- 配对发现成功就等于 TLS、MQTT 登录及业务上报成功。

## 3. 建议冻结的总体方案

### 3.1 继续保留 auto

GH_N3W_PAIRING_ADVERTISED_HOST=auto 继续负责配对发现，返回当前 Manager 的地址。

配对成功后，通过现有可信配对通道下发稳定 Broker 名称、TLS 校验名称、CA 和节点专属凭据。日常业务连接按稳定名称寻找 Broker。

B2 不是将 auto 替换成 .local；也不把配对 HTTP 地址直接当成可信 Broker 身份。

### 3.2 一个逻辑 T1 服务对应一个持久稳定名称

建议形式为 gh-t1-<稳定标识>.local。

- 首先检查现有 SYSTEM_ID、MANAGER_ID 的唯一性、恢复语义和长度，优先复用合适的完整标识；不截成短短几位，不用客户姓名、安装地点、IP 或容器 ID 生成。
- 若已有标识不能满足合同，才新增一次生成并持久化的随机端点标识；不为了命名建立第二套节点身份系统。
- 名称在初始化成功后持久保存，不因重启、容器重建、网卡更换或 DHCP 变化而重算。
- 更换物理 T1 并恢复同一系统的完整备份时，应继承原服务名称。原主机必须退出，禁止两台机器同时使用同一份身份和私钥提供服务。
- 同一系统未来多活、热备或多个 Broker 不属于 V1；不能提前用复杂选举机制解决尚不存在的需求。
- 用户可以修改显示名称，例如“东棚主机”；显示名称不改变协议名称、证书或节点信任。

这里的“每台 T1 唯一”更准确地说是“每个独立的 T1 服务身份唯一”，不是把名称永久绑死到不可更换的硬件。

### 3.3 V1 的支持范围

建议先支持：

- 同一局域网链路，节点与 T1 可互访。
- IPv4 业务连接与名称解析。
- 单 T1 服务身份，多节点；同一局域网可有多个彼此独立的 T1 系统。
- 离线本地运行，不把厂商云或公共 DNS 作为名称解析的必需条件。
- 一份同型号生产固件，通过首次配置获得部署专属信息。

不作为 V1 必达项：跨 VLAN 自动发现、互联网远程寻址、IPv6 业务接入、双活 Broker、自动接受未知 CA、全自动处理私钥泄露后的信任重建。

IPv4-only 是本功能发布和消费地址的边界，不授权全局关闭操作系统 IPv6，不能破坏 Home Assistant 等现有服务。

### 3.4 名称解析与身份校验严格分开

名称解析回答“去哪个地址连接”；TLS 回答“对方是否是我已信任的服务”。

无论地址来自 mDNS、普通 DNS 或未来回退发现，节点必须始终使用已绑定的 broker_tls_server_name 和 CA 校验对方。成功验证之前不发送 MQTT 用户名、密码或业务数据。不能从未认证的发现回应或 TXT 记录替换 CA、名称或系统归属。

不关闭主机名检查，不回退明文，不把证书错误当成单纯地址错误无限重试。

### 3.5 mDNS 失败时的路线

基础版本先保证正常 mDNS 网络完整闭环；解析失败时继续本地采集、保留绑定，有限重试并给出可理解的状态。

在接口冻结阶段评估是否能低成本复用现有 UDP 发现，形成受限回退：

1. 仅在节点有已绑定身份时运行。
2. 回应仅作为临时 IP 线索，响应匹配当前请求；系统标识只是筛选线索，不是身份凭证。
3. 仅在“Manager 与 Broker 同机且端口已可信配置”的部署合同下，才可把候选地址用于 Broker TLS 尝试。
4. 仍校验原 CA 和原 TLS 名称，不接受回应提供的新信任根，不重新配对。
5. 限制候选数量、查询频率、总时间；成功前不覆盖长期配置。
6. 限于当前合法 LAN 地址；拒绝回环、组播、未指定地址及不允许的地址范围。

若上述方式需要新增一套有状态发现协议、跨服务地址映射或身份更新流程，则划入 B2 后续增强，不挤进基础版本。基础版本可以在公布的 mDNS 支持范围内交付，但不能宣称所有路由器均免配置。B3 另行解决旧数字 IP 的迁移。

## 4. 五个开发工作包

### 工作包 A：T1 初始化、名称发布与网络生命周期

A1. 初始化与持久化：

- 将稳定名称绑定到已有系统初始化记录，明确写入位置、文件权限、备份成员和版本。
- 全新系统自动初始化；已有系统加载旧身份；目录残缺或校验失败时停止，不偷偷生成新 CA 或新名称。
- 处理并发初始化、磁盘满、只读盘、断电和重复启动。
- 出厂镜像不包含已初始化的客户身份、CA 私钥、节点凭据或克隆的系统标识。
- 开发 T1 的存量身份采用显式接纳流程，不能执行“全新初始化”。

A2. 名称发布：

- 盘点现有 Avahi、systemd-resolved、HA 相关发布服务、UDP/5353 占用和监听接口。
- 优先复用 T1 已有成熟发布服务；没有时采用一个系统级发布器，不在 Manager 和另一个容器里重复写两套响应器。
- 如果使用 Avahi，配置由产品安装流程管理，处理其启动、重启、地址更新和异常退出。
- 优先使用受控服务别名或受支持的地址记录注册方式，不随意修改整台开发主机的系统 hostname。
- 名称记录只发布受支持的业务 LAN IPv4，排除回环、Docker bridge、VPN、维护口和已失效地址。
- 网卡地址变化时撤销或刷新旧记录，按协议更新缓存；不能靠一次性写死 hosts 文件。
- DHCP 暂不可用时不宣称名称就绪；重新获得地址后自动恢复。
- 一个名称只有一个明确维护者，记录实际发布名称是否与证书及下发配置一致。
- 多网卡首版如只支持指定业务接口，必须显式声明；不能假定默认路由所在接口一定是用户业务 LAN。

A3. 冲突与服务生命周期：

- 第一次尚未建立任何绑定前，名称冲突可以受控生成新候选，并在证书和持久化记录同步成功后启用。
- 已有节点绑定后发生冲突，不允许后台悄悄改名加“-2”；暂停冲突发布、告警并走受控处理。
- 不在支持稳定名称的系统里采用持续高频广播；按成熟协议栈处理请求与网络变化。
- 地址记录可在 Broker 暂停时保留；“业务可用”状态另行判断，不能把名称可解析当作服务健康。

A4. 网络安全：

- UDP/5353 发布/查询只在允许的 LAN 接口上工作；需要新增规则时单独记录、验证来源范围。
- 不启用跨接口 mDNS reflector，不扩大为 WAN 发布。
- 保持 Broker 现有单一显式 IPv4 通配 TLS publication、完整双网络 attachment、入口限制。
- 保持 Manager host network 与无 ports publication；本机 Broker 访问继续走已验证的 loopback TLS 路径。

通过条件：新 T1 独立初始化后名称不同；同一 T1 重启和地址变化后名称不变；外部测试客户端能看到当前地址；无容器私网地址泄漏或接口范围扩大。

### 工作包 B：证书签发、续期与恢复

B1. 初始签发：

- 复用已有每系统 CA；为 Broker 签发包含稳定名称的服务端证书，使用 SAN DNS 名称。
- Broker 仅取得服务端私钥和证书，不取得 CA 私钥；CA 签发入口具有限制权限，不暴露在公共配对 API 中。
- 若 Manager、HA 现有客户端使用其他校验名称，先列清真实名称，在同一系统受控范围内保留必要兼容 SAN；不得直接删除旧名称使它们失联。
- 不要求为每个节点新建客户端 TLS 证书；沿用每节点独立 MQTT 凭据和最小权限。
- 配对下发的名称、CA、端口来自同一持久化端点合同，禁止多个环境变量各自漂移。

B2. 日常续期：

- 建议初始目标：叶证书有效期 1 年、剩余 30 天前开始续期；最终值在设计评审冻结，不是现有实现事实。
- 同一名称、同一 CA 的续期不需要每台节点重新配对或重新下发 CA。
- 使用受限的定时任务或现有维护入口，避免仅为续期新增常驻业务平台。
- 先在候选位置生成并检查证书、私钥匹配、名称、用途、有效期和权限，再原子切换完整证书对。
- 用目标 Mosquitto 版本验证 reload 行为和挂载可见性；尤其检查单文件 bind mount 是否会继续看到旧 inode。
- 切换后建立新的 TLS 会话检查新证书，而不是用已有 MQTT 长连接证明续期成功。
- 失败时恢复仍有效的旧证书并告警；旧证书已过期时，回滚只能恢复文件，不能宣称服务恢复。
- 续期不变更 DynSec 数据、节点密码、业务权限或信任根。
- 测试旧连接与新连接的行为；必要时采用有预算的重连，不承诺任意版本绝对无感。

B3. 时间与长期离线：

- 核对 T1 和 ESP32-C6 的实际时间来源、冷启动时间、断网保持方式和证书日期检查配置。
- 首次安全配对可评估携带受保护的可信时间信息；已绑定节点的冷启动不能依赖“先完成需要正确时间的 Broker TLS，才能校时”的循环。
- 阶段设计必须落实无公网环境的校时/时间保持方案。若要引入认证时间响应，应单独冻结用途、请求新鲜性、权限和防重放边界，不重做配对协议。
- 普通 NTP 不是天然可信时间源；记录威胁模型、合理范围检查、已知时间下界及失败行为，不以任意广播时间绕过过期校验。
- 时间不可用时继续本地监测、提示时间问题，不能静默跳过证书日期检查。
- 如果不能在目标网络下解决冷启动时间问题，则“离线无人值守生产可用”的验收不通过。

B4. CA 与主机恢复：

- 自动叶证书续期是 B2 基础能力；CA 到期/泄露后的自动信任迁移是另一等级问题。
- 首版至少提供 CA 到期提前告警、完整加密备份、授权维护和离线节点恢复说明。
- CA 自动轮换可后续开发，但不得把“有效期很长”描述为永远无需维护。
- 有效备份恢复需成套恢复身份、CA、Broker 凭据库、Manager 注册及相关状态；不能只复制证书。
- 无备份或 CA 泄露时停止自动接管，不通过 mDNS 下载一个新 CA 自行相信。
- 固件内不装每户 CA 私钥，不使用全球共享客户私钥。

通过条件：正确证书通过；错名称、错 CA、过期、未生效证书均拒绝；日常续期后节点无需重新配对；断电或切换失败可以恢复到明确状态。

### 工作包 C：Manager 配对配置与首次配置体验

- 保留 auto 发现和当前一次性秘密/用户确认机制，不另开绕过授权的配置接口。
- 新系统默认下发稳定名称。地址、TLS 名称和 CA 分开保存，但其关系必须被验证。
- 新生产配置不应默默使用 mqtt.greenhouse.local 这样的全局占位名称；存量兼容必须显式识别，不能将已有部署一刀切改坏。
- UI 显示友好名称及足够区分系统的信息，多 T1 时用户明确选择；不按最快回应、信号强度或字典顺序自动建立归属。
- 同一请求重试保持现有幂等语义；不重复生成 NODE_ID，不重复授权凭据，不因名称暂未解析成功消耗掉唯一恢复机会。
- 配对流程复用现有暂存、提交和失败恢复能力；先审计现有状态再决定是否需要最小扩展。
- 页面区分“已找到主机”“等待用户确认”“正在验证安全连接”“已加入、等待数据”等用户能理解的状态。
- 成功条件至少包括安全连接和 MQTT 身份接受；最终端到端验收还必须看到 Manager 的实际状态数据前进。
- HTTP 200、hello rejected、收到凭据、名称解析成功均不能单独显示“已完成”。
- 继续保持原有已注册身份修复门禁；网络变化不自动触发 repair 或覆盖既有身份。
- 保留当前 KF-099 的配对重试边界作为回归，不将 B2 混同为身份修复。

通过条件：用户无需输入主机地址或证书；多个 T1 不串绑；真实端点生成的配对包被板端正确接收，首次 MQTT 与业务路径完成闭环。

### 工作包 D：节点名称解析、MQTT 与持久化

D1. 生产接入：

- 在正式生产构建上核对 ESPHome/ESP-IDF 和 mDNS 组件版本，先判断是否已有可用解析器。
- 优先复用已有查询能力；只能有一个明确的 mDNS 生命周期所有者，避免重复初始化或释放其他组件正在使用的实例。
- 从真实 MQTT 配置入口向下检查 .local 最终如何解析。能设置 broker_host，不等于当前 getaddrinfo 路径必然支持 mDNS。
- 若默认路径不满足要求，增加小型地址解析适配层：持久保存名称，只在内存中保存短期连接地址；TLS 仍使用原名称。
- 现有 TLS 名称补丁必须在实际依赖版本上验证，包括编译、运行和错误名称拒绝；不能只靠补丁字符串存在。
- 不因 B2 一起升级整个 ESPHome/ESP-IDF 工具链。

D2. 重连与资源：

- Wi-Fi 获得地址、网络改变、MQTT 连接失败后按既定策略重新解析，不无限复用旧 IP。
- 缓存有期限并能主动失效；网络切换使旧异步查询结果失效，迟到回调不能把新网络地址换回旧值。
- 名称查询、TCP、TLS 和 MQTT 都有超时，使用统一的上层恢复预算；不能每进入一个子步骤就重置整轮预算。
- 成功连接时不持续查询或反复写 NVS；DHCP 改变只更新临时连接地址，不改系统身份或 credential_generation。
- 区分解析失败、TCP 不通、TLS 身份错误、凭据被拒绝、服务暂停和时间未就绪。
- 使用有上限的退避和抖动，避免多节点同时重连造成风暴；不形成每几秒重启整板的处理方式。
- 网络任务不阻塞传感器、LCD、看门狗和电源管理。

D3. 与 Direct/Relay 的关系：

- 名称解析只在当前无线所有权允许的 Wi-Fi/IP 窗口内执行。
- 不为 mDNS 查询自行启动 STA、扫描或切换信道。
- 健康 Relay 的 Direct 尝试仍共享原有 30 秒上限；查询、TLS、MQTT 的时间都算在里面。
- 取消或超时后释放资源，按既有顺序恢复物理 Relay 无线状态。
- 不改 KF-094/095/096 的既定策略，不重做 PR #474；只测试新代码没有侵占其预算和所有权。
- Relay 子节点不因本机解析失败而丢弃仍健康的 Relay；上游网关需具备自己的 B2 连接能力。

D4. 持久化与兼容：

- 优先用已有 broker_host、broker_tls_server_name 和 ca_pem，不增加“永久 IP 缓存”。
- 当前板端 CA 内容上限约 4096 字节，而 Manager 配置文件检查上限为 64 KiB；新交付必须按两端最小可用容量做验证，不能等到实机解密后才发现装不下。
- 冻结名称长度、合法字符、大小写/末尾点处理、证书链大小、总加密包长度、HTTP 缓冲区、NVS 记录和 RAM 峰值。
- 如无需新增持久字段，保留现有格式；如必须变更，提供版本识别、断电安全和明确回退支持。
- 不能因新的“禁止数字 IP”规则让尚未迁移的旧节点无法启动；存量数字 IP 由 B3 处理。
- 断电恢复后仍保留已获批的身份和有效凭据，不能把解析故障当成恢复出厂。

通过条件：真实节点按名称连接；地址变化后重新解析成功；攻击或错误证书不能诱导提交 MQTT 凭据；本地功能和健康 Relay 不退化。

### 工作包 E：部署、量产和可观测性

- 建立单一诊断入口，分别报告初始化、名称发布、名称解析、TCP、TLS、MQTT 和业务状态。
- 错误信息面向用户可理解；详细诊断中只存必要非敏感数据，不输出密码、Setup Secret、私钥或完整配对报文。
- 发布就绪检测必须从独立客户端或实际节点观察；仅 T1 自己解析自己不能代表 LAN 可用。
- 分离“可解析”“可 TLS 连接”“可 MQTT 登录”“数据到达 Manager”四个结果。
- 工厂镜像扫描确认没有客户专属地址、名称、信任根私钥、Wi-Fi 或节点密码。
- 首次启动创建唯一身份；恢复镜像根据明确的恢复模式使用备份，不能与全新初始化混淆。
- 每个新模块必须实际接入现有 CLI、服务启动或正式固件调用链；只被测试导入不算开发完成。
- 安装、升级和卸载均记录自己的文件及规则，不能覆盖不归本功能管理的 Avahi、HA 或防火墙配置。

## 7. 指标与观测方法

所有数值是建议验收目标，需在 G1 按实测基线冻结。不能为满足新指标放宽既有更严格约束。

| 指标 | 建议目标 | 说明 |
|---|---|---|
| 用户手工输入主机 IP、证书、端口 | 0 次 | 联网和一次明确归属确认除外 |
| 正常 LAN 单次解析预算 | 不超过 3 秒 | 作为子步骤预算，不增加无线整轮预算 |
| 地址恢复后的解析/TLS/MQTT尝试 | 已知网络变化应在下一允许的恢复窗口执行 | 不能在健康 Relay 中立即抢占射频 |
| 正常 Direct 场景恢复 | 网络、发布和 Broker 均就绪后，建议 60 秒内业务继续 | 区分失联检测、退避等待与连接耗时 |
| 健康 Relay 的 Direct 试探 | 原 30 秒整轮上限保持 | 不再为解析/TLS额外增加窗口 |
| 退避后的最坏恢复时间 | 明确公式并实测 | 检测时间+剩余退避+连接预算，不只报最佳值 |
| 基线/观察窗口 | 90 秒/600 秒 | 按当前项目习惯 |
| 地址切换重复 | 物理至少 3 轮；隔离自动化建议 100 轮 | 不是 100 次破坏生产网络 |
| 长稳 | 24 小时基础；规模试点可延长到 72 小时 | 报告实际窗口，不用短测替代 |
| B2 导致的非预期节点重启 | 0 | 主动断电测试单独标识 |
| 归属/节点编号/HA 实体变化 | 0 | 网络故障不改身份 |
| DHCP 地址变化带来的 NVS 配置写入 | 0 | 仅刷新内存中的连接地址 |
| 资源 | 记录空闲堆、最大连续块、栈余量、镜像大小及功耗增量 | 具体上限依据 G0 基线冻结，不虚设容量 |

每次地址变化至少记录：

1. 网络变化时间、节点知晓时间、旧连接失效时间。
2. 新地址可用与发布更新的时间。
3. 节点重新解析、TLS 完成、MQTT 接受的时间。
4. Manager 第一条新数据及随后至少两次序列前进。
5. boot 是否变化、身份和凭据代数是否变化、HA 实体是否变化。
6. 失败原因和是否自动恢复。

必须拆分“连接恢复”与“业务恢复”。不能用 ping、TCP 握手、MQTT connected 或日志一条成功替代 Manager 实际数据前进。

- GitHub CI 或隔离 Linux：Docker、Mosquitto、证书、网络命名空间及负例。不能用生产 T1 作 CI runner。
- 实机：ESP32-C6 的真实解析、TLS、断电、内存/功耗和单射频行为。
- T1 现场：部署前只读基线、明确变更、回滚、Manager/HA/Broker 连续性及外部接口负例。

证据必须绑定源码提交、工具链、镜像/固件摘要、设备身份摘要、测试起止时间和用例编号。公开记录结果、摘要和非敏感原因；原始抓包、密钥、授权材料只放私有证据位置，公开留摘要与用途。

测试标记至少区分：未执行、通过、失败、不适用；不适用必须有理由。CI 通过与实机通过分别记录。

源代码字符串检查仅用于补充防回归，关键状态行为必须直接运行实际模块。正式 MQTT 路径、初始化入口和续期入口都必须有集成测试证明可达。

## 9. T1 上线与回滚顺序

部署前必须有可审阅的执行包和回滚包。本规划不是现场执行授权。

1. 只读固定当前容器镜像、所有挂载、环境、网络、证书、名称发布者和规则；以实际运行容器为准，不用不完整 Compose 猜配置。
2. 验证完整备份可读取、摘要匹配、恢复工具可用。
3. 准备新名称与兼容证书，保留已有服务实际需要的旧名称；不改节点凭据库。
4. 在隔离环境或 shadow 中验证完整运行合同。正式部署前不宣称现场可用。
5. 分阶段启用 T1 发布和证书；先验证 exact Manager loopback 与 HA，再允许新测试节点加入。
6. 单板通过后再进入多板和换地址测试，禁止一次迁移全部现有设备。
7. 每阶段失败要区分“修改前停止”和“已经修改后回滚”；回滚验证到真实服务，不只检查文件还原。

回滚分界：

- 尚未下发 B2 配置：通常可以恢复旧发布和证书配置。
- 已有节点保存新名称：不能直接撤销新名称或改回不包含该名称的证书。必须保留兼容服务，或先完成明确的节点反向迁移。
- 已发生持久化格式升级：仅允许回退到已验证能读取该状态的固件。
- 已撤销的身份或凭据不得因旧备份恢复而自动复活。

部署顺序倾向“T1 先具备兼容能力 → 板端上线 → 新节点验证 → 旧节点迁移”。其中最后一步属于 B3。

## 10. 完成定义与状态

B2 只能在下列条件全部满足后标记完成：

- 名称由系统自动生成/接纳并持久化，重启和地址变化不变。
- 业务 LAN 发布和实际节点解析通过；多 T1 不串绑。
- 新节点统一固件、零手填地址和证书，首次安全配对与业务上报通过。
- 真正按名称验证证书，所有关键安全负例拒绝。
- 同 CA 叶证书自动续期成功，并有失败回滚。
- 无公网冷启动的时间方案通过目标验收，或明确收窄产品承诺后重新评审。
- 地址变化和重启后自动恢复，不需要重新配对。
- 健康 Relay 预算与射频所有权、本地采集/LCD/功耗边界保持。
- T1 部署、备份恢复、兼容和回滚实际验证通过。
- 关键证据已归档，未执行项目如实列出。

建议分项状态为：

- B2_DESIGN：设计冻结。
- B2_T1_SOURCE / B2_FIRMWARE_SOURCE：源码与测试完成。
- B2_FIRST_SETUP：首次配置实机通过。
- B2_ADDRESS_CHANGE：地址变化实机通过。
- B2_CERTIFICATE_LIFECYCLE：签发/续期/时间/失败恢复通过。
- B2_PRODUCTION_READINESS：完整发布验收通过。

不能用一个“mDNS 测试通过”代替所有状态。

阻断项包括：错误证书被接受、发现包能替换信任、身份被重建、时间检查被绕过、健康 Relay 超预算、错误接口发布、不可恢复的存储损坏、上线使原 Manager/HA 失联、关键正式入口未接通。

B2 完成不关闭 B3，也不自动确认既有 A/B/C 全部恢复。

## 11. B3 的衔接

B2 输出给 B3 的是：稳定名称合同、信任材料、板端支持版本、兼容清单、地址更新/持久化边界和可验证的新目标。

B3 再逐板决定：

- 已支持名称但保存数字 IP：通过现有授权配置更新迁移。
- 当前固件缺少所需解析能力：先安排保留身份的固件升级，再迁移配置。
- 旧 MQTT 地址已不可达：不能依赖旧 MQTT 连接下发新地址，需要另一个已验证的恢复入口。
- 另有身份/凭据问题：进入独立身份修复流程，不把地址迁移做成清库或重新注册。

B3 迁移保留同一未退役硬件的合法归属和 HA 数据关系；不得用旧路线中“跨硬件复用 NODE_ID”的已废弃说法。更换板卡、退役后重配按当前身份规则处理。
