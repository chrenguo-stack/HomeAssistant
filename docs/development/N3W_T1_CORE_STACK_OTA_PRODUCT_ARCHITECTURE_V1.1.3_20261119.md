# T1_Core_Stack OTA 架构设计方案 V1.1.3

**定稿日期**　2026-11-19  
**修订说明**　V1.1.3 将 OTA 终态正式收敛为严格二态：`SUCCESS` 或 `FAILURE`。status/checker 自身异常不能伪造成“新版软件已被证明失败”，但在限定补验后仍无法证明新版满足验收合同时，本次 OTA 必须判定为 `FAILURE` 并自动恢复升级前的健康版本；不得形成 `PENDING`、`SAFE_HOLD`、`NEEDS_SUPPORT` 等第三种 OTA 终态。V1.1.3 取代尚未合并 `main` 的 V1.1.2。  
**适用产品**　斐讯 T1 上由 greenhouse-manager（Manager）、Mosquitto（Broker）和 Home Assistant（HA）组成的温室监测系统。  
**文档状态**　产品架构定稿，供后续开发和验收使用。源代码完成情况和实机结论以各自的验收记录为准。

## 1. 产品承诺与边界

用户点击安装后可以离开。OTA 事务的**终态结果只有两种**：`SUCCESS` 或 `FAILURE`。`SUCCESS` 表示新版已经通过健康验收并提交；`FAILURE` 表示本次升级没有满足提交条件，且系统已经自动恢复到升级前的健康版本。判断、重试、恢复和最终确认均由 T1 完成。用户不需要查看日志、判断数据是否正确，或点按钮确认升级结果。升级中、恢复中、等待重试等都只是过程状态，不是第三种 OTA 结果。

安装期间允许提前告知的功能暂停。以 HA 更新为例，备份期间 HA 和 Manager 可以停止，Broker 可以继续提供服务；依赖 HA 或 Manager 的页面、数据接收、历史展示和相关告警可能暂停。节点按现有能力采样、本地显示、暂存和补传。缓存溢出造成的曲线缺口允许保留。**停机前已有的受保护配置、配对、凭据和保留期内的历史，与停机期间可能缺失的新采样，分别验收。**

承诺的前提是主机能重新供电和启动、内部存储和 Docker 可工作。OTA 在进入破坏性切换前必须证明至少一条可自动执行的前代恢复路径成立；包含 HA 的发布优先使用已验证的绑定 U 盘恢复材料，并保留可核对的前代身份。断电或进程退出后由主机自行接管。确实需要原盘时，提示插回，识别后自动继续；这仍属于 `RECOVERING` 过程，不是第三种终态。若发生内部存储物理损坏、介质物理损坏等超出 OTA 能控制的设备故障，应归入独立的设备故障域，而不是发明第三种 OTA 结果。

## 2. 继承 V1.0 的决定

| 设计项 | V1.1 约定 |
| --- | --- |
| 产品入口与发布单位 | 一个系统更新入口。发布单位为三组件的已批准兼容组合，只替换确需改变的组件。用户可以检查、准备、安装、查看状态。 |
| 现有执行器 | 宿主机上的 `T1_Core_Updater` 是唯一特权执行器。Manager/HA 通过现有受限本地接口提交意图。它们不能传入任意命令、路径、设备或下载地址，也不获得 Docker 套接字或 root 权限。 |
| 组件升级方式 | Manager 复用 Generic V2 切换能力。Broker 沿用 Generic V2 方向并单独验证持久状态。包含 HA 镜像变化的发布必须使用 USB。仅改变 Manager、Broker 或两者时沿用本机恢复策略，容量不足即不准入。 |
| 发布可信性 | 产品通过限定的 HTTPS 来源取得签名索引和签名发布清单，使用本地信任根校验签名。清单约束发布身份、三组件目标组合、平台、包大小与摘要、前代及回滚兼容性、最低执行器版本。安装顺序由本地规则决定。GitHub Actions 产物保留作工程用途。 |
| 事务与工程积累 | 沿用主机持久事务、组件适配器和 HA 的 U0–U13 记录。多组件逐个切换，整套通过后一次提交。既有测试、归档和一次性执行记录继续可追溯。工程阶段编号不作为用户操作步骤。 |

相对于 V1.0，本版修订 USB 准入、旧版恢复方式、第一次停服后的接管、数据校验和公开进度。V1.0 中的特定现场版本号、开发停点和授权不用于判定客户设备的当前状态。当前版本以设备最后接受的发布记录和实际运行镜像共同确定。

## 3. 一笔 OTA 的四个阶段

四个阶段供产品和开发使用。主机复用原有事务记录，无需再维护一份平行状态机。

| 阶段 | 主机动作 | 进入下一步的条件 | 中断后的默认动作 |
| --- | --- | --- | --- |
| ① 在线准备 | 旧版继续服务。核对当前健康基线、版本兼容性、介质和双向空间；准备目标包及旧镜像，验证可读，记录适用的业务检查。 | 材料齐备，可接受针对这个发布的安装请求。提示本次影响及 USB 使用要求。 | 保持旧版。下载失败、基线无法确认或空间不足可在以后重新准备。 |
| ② 建立恢复点 | 安装请求到达后重核身份和容量。**第一次停服前**先持久记录谁负责恢复、原运行组合、启动方法及受影响组件。随后静止必要的写入方，制作并验证一致备份。 | 在第一项不可逆操作前，整套发布受影响组件的旧镜像、配置、受保护数据及恢复顺序均已落实。 | 旧镜像和数据仍完整时自动启动已停服务，验证旧版健康。备份失败不得把服务留在停机状态。 |
| ③ 切换与试运行 | 逐组件执行，先记意图，再做动作，最后核对现场并记录结果。HA 只在恢复点成立后释放内部旧镜像空间，再导入目标。按依赖启动服务。 | 每个已动组件达到本阶段要求，整套进入健康验收。 | 依据实际保留的镜像、数据是否可能被新版写入、已动组件集合，选择第 5 节的恢复路径。 |
| ④ 验收与结束 | 自动验证运行版本、配置、历史和本机监测接收路径。新版全部必检项通过后，持久提交新组合。回滚后以相同健康合同验收旧组合。 | 新版已提交，或旧版已恢复。随后刷新并安全卸载 USB，分别报告业务状态与拔盘状态。 | 已提交时恢复公开状态和收尾。回滚中的断点只续做未完成动作。卸载、页面刷新或上传诊断失败不触发业务回滚。 |

**三个关键时刻需单独记录。** 第一次停服即产生恢复责任，在现有 HA 路径中对应 U6 到 U7 的交界。旧镜像实际从内部存储释放才改变恢复手段，U9 的授权已消费本身无法证明 U10 已删除镜像。整套发布的提交记录写入成功才结束本笔自动回滚权限。

## 4. U 盘、容量与数据写入

1. **兼容且可用即可。** 使用已经通过本机读写、完整落盘、断电恢复和大文件测试的文件系统。产品列出支持的格式。允许非空盘、任意卷标和设备名变化。沿用 V1.0 的文件系统实测可用总容量至少 14 GiB、选购建议 16 GB 或更大；另外核算当时的实际剩余空间。格式不支持、只读或空间不足时，在停服前说明原因或提示换盘。OTA 不提供格式化流程。
2. **只向本笔新目录写入。** 在盘上创建 `N3W-OTA/<事务标识>/`。目录冲突或路径指向其他位置时拒绝写入；本笔恢复时先验证已有内容的归属。工件和进度记录使用新文件或新代次。升级、回滚、重试、成功收尾及下一次升级都不删除或覆盖盘上已有文件，包括旧 OTA 文件和未完成文件。空间不足提示换盘，由用户自行决定盘上资料的去留。
3. **原盘绑定可跨重启。** 用文件系统 UUID、事务身份及已验证工件共同确认，忽略 `/dev/sdX` 排序和盘符。需要读写介质时确认挂载点仍对应原盘，防止误写落入 T1 内部空挂载目录。若有多个合格介质且无法唯一识别，停留在准备阶段并提示只接入本次用盘。
4. **分别计算安装和恢复的峰值。** USB 预算含目标包、旧镜像、受保护数据备份、临时写入及余量；内部预算含镜像导入解包、共享层实际可释放量、数据迁移或恢复工作空间、事务记录余量。禁止以压缩包大小代替内部峰值。最终静止数据大小超出估算时，保持旧镜像并启动旧版。只能释放本事务独占且身份已核实的内部资源，禁止全局镜像清理。
5. **备份可以独立使用。** 旧镜像从设备实际运行的前代导出并绑定平台和内容身份，完整落盘后从 USB 回读校验。受保护数据沿用经认证的加密备份，验证解密和内容清单；密钥在宿主受保护位置可供恢复使用。开始切换后，正常完成或恢复均可离线执行。
6. **提交前保护用户修改。** 从静止备份起，到新版本持久提交或旧版恢复前，受本次回滚影响的配置入口、配对和凭据变更暂缓接受，页面可读时清楚提示。若某版无法约束相关写入入口，且回滚会丢掉已向用户确认的修改，该发布不得进入安装。试运行期间的遥测按维护窗口处理，允许补传或缺口。提交后重新开放修改，本笔 OTA 不得再用旧快照覆盖新写入。

## 5. 自动恢复与断电接管

宿主机复用现有执行器和恢复原语。正常执行、进程重启及开机接管使用同一事务锁和同一恢复实现。关闭页面、Manager 停止、安装进程异常或探针抛错，都不能取消主机的恢复责任。

| 主机能确认的事实 | 自动处置 |
| --- | --- |
| 已经停服，旧镜像、启动配置和原数据可用；新版没有机会写入数据 | 启动原服务，验收旧版。跳过无必要的数据回写。 |
| 内部旧镜像已释放；能证明原数据未被新版或迁移程序写入 | 从绑定的 USB 导回旧镜像，使用原数据启动。 |
| 新版或迁移程序可能写过数据，或写入事实无法判明 | 停住相关写入方，恢复同一恢复点的旧镜像、启动配置和受保护数据；静止核对后启动。禁止让旧版试开可能已迁移的数据。 |
| 多组件发布中途失败 | 按已验证的依赖顺序恢复本笔已动部分，核对未动组件，最终回到升级前的兼容组合。单个组件通过只表示可以继续。 |
| 程序在系统动作和事务落盘之间退出 | 重新取锁，核对已持久化的意图、实际容器/镜像、写入边界及材料身份。已做的动作直接认领结果；不能证实安全前进且业务中断时，走可证明安全的旧版恢复路径。 |
| 需要的原盘暂时不可读 | 能从内部安全启动旧版时先恢复服务；确实依赖原盘时保留现场，提示插回原盘，匹配后自动续办。 |
| 旧版已在提供服务，但某项终态证据尚未取得 | 维持已恢复的服务，显示已确认的可用功能及待核验项，自动复核；禁止重复覆盖数据、反复重启或开始下一笔升级。 |
| 已持久提交新版，或已验收并持久记录旧版恢复 | 重启只恢复该结果和未完成的收尾。重复点击安装、重复通知、前端断线重连均不得重复执行。 |

主机事务至少持久保存事务标识、前后发布、组件身份、规则版本、恢复材料引用、动作意图及完成事实。对关键边界采用可承受断电的原子落盘。主机记录是主记录，USB 保存可核对的恢复材料及本笔追加记录。遇到冲突时先只读核对材料与现场，不凭较大的阶段号推进。已消费的操作授权不重放。正常开机也不能默默发起新升级。

每个动作都定义可观察的进展、允许的重试次数和停止条件，例如新增的落盘字节、镜像导入子步骤或服务启动状态。处理慢速 USB 和数据库迁移时，只要有有效进展就继续。探测本身采用有限等待和重试；确认原写入者已经停止后才能接手。恢复仍不能进行时，保留可用服务、材料及明确状态，不循环切换版本。产品不对用户承诺统一的升级或恢复分钟数。

### 5.1 恢复链路与观察链路强制解耦

恢复是最高优先级的本地安全职责。**状态接口不得成为恢复流程的前置条件；checker、Manager、HA 页面或其他 UI 的异常，不得取消、暂停或阻断已经成立的恢复责任。** 恢复程序直接读取主机持久事务、恢复材料和实际运行事实决定下一步，不能依赖某个前端是否在线、某次 status 查询是否成功，或某个 checker 是否返回完整结果。

本系统把 OTA 运行责任明确分成四层，低层观察能力不得反向控制高优先级恢复：

1. **恢复引擎。** 负责断电接管、旧版启动、介质等待、回滚和最终健康恢复，是唯一必须在 Manager、HA 或 UI 不可用时仍能工作的层。
2. **OTA 控制层。** 负责准备、安装、事务推进和受限控制；控制接口异常时不能撤销已经持久化的恢复责任。
3. **状态与 checker 层。** 只观察和解释事实，允许部分字段不可得。它可以阻止一个未经证明安全的危险写动作，但不能因为自身异常而停止一个已经需要执行的安全恢复动作。
4. **UI 层。** 只显示状态和用户提示。页面断开、刷新失败或版本不匹配不得改变 OTA 事务。

状态接口必须先返回**核心事务状态**，再尝试附加容量、进度、候选介质等非核心信息。附加信息失败时，核心状态保持有效，例如：

```text
accepted=true
phase=RECOVERY_MEDIA_REQUIRED
error_code=null
status_detail_degraded=true
usb_capacity_check_state=UNKNOWN
```

禁止因为一个非核心字段读取失败，把已经正确识别的 `RECOVERY_MEDIA_REQUIRED`、`ROLLING_BACK` 或 `ROLLED_BACK` 整体改写为 `accepted=false`、`ota_status_rejected` 或通用 `ERROR`。

**状态读取按阶段隔离。** U1–U5 的准备状态提供器只服务准备阶段；U6–U8 使用恢复点/备份状态；U9–U13 使用切换与恢复状态。进入 U10 后不得再把 U1–U5 的 prepare 状态作为核心 status 的必需依赖。跨阶段附加信息只能在明确支持该阶段时读取，否则返回“未知/不适用”，不能抛出足以覆盖核心状态的错误。

异常仍需分类，但**分类不能产生第三种 OTA 终态**：

| 异常类型 | 例子 | 处置 |
| --- | --- | --- |
| 观察链路异常 | status 编码失败、容量附加信息读取失败、checker 超时、Manager/UI 读不到状态 | 核心事务继续；先使用限定重试和独立证据补验。若仍无法证明新版满足提交条件，本次 OTA 记为失败路径并自动恢复前代。 |
| 核心事实明确不安全 | 签名/摘要不匹配、绑定 U 盘身份错误、事务授权矛盾、恢复材料校验失败 | 危险写操作立即 fail-closed；未切换时保持旧版，已切换时自动恢复前代。最终 OTA 结果为 `FAILURE`。 |
| 核心事实无法判明 | 事务文件损坏、恢复材料身份冲突、无法确认已执行到哪一步 | 不继续向新版方向推进，不重放授权，不格式化介质；按持久意图、实际镜像/容器和已验证恢复材料选择最保守的前代恢复路径。事务在恢复完成前保持 `RECOVERING`，恢复健康后终态写 `FAILURE`。 |

`RECOVERING`、`WAITING_FOR_MEDIA` 等只能是**过程状态**。它们不得被持久化为 OTA 的最终结果，也不得在 UI 上作为“第三种升级结果”展示。

**查询 status 本身必须只读。** status/checker 查询不得触发服务重启、介质写入、事务推进、镜像装载或授权消费。需要修复观察链路时，修复动作必须作为独立、可审计、受限操作执行，并在修复前后证明核心事务未被推进。

### 5.2 升级执行、升级验收与状态展示强制解耦

升级链路采用与恢复链路相同的原则：**执行事实、验收判定、状态展示是三个不同层次。** 新版镜像是否已导入、服务是否已启动、业务是否健康、status 是否能正常显示，必须分别记录，禁止用一个接口的成败代替另一个事实。

升级执行器只依据持久事务和经过授权的动作推进。例如 U10 → U11 的镜像导入和服务启动必须由执行器记录真实动作结果；status 查询成功、checker 正常返回或 UI 显示“正在升级”都不能证明该动作已完成。反过来，status/checker 自身异常也不能把已经完成的升级动作改写成失败。

新版启动后的**验收证据**可以有三种内部语义，但 OTA **事务结果仍严格二态**：

- **PASS：** 已取得本阶段要求的明确业务证据，可以提交新版。
- **PROVEN_FAIL：** 已取得明确反例，证明新版或本次升级结果不满足健康合同，进入受控恢复。
- **EVIDENCE_UNAVAILABLE：** 验收器、status、数据源、协议或附加查询自身异常，暂时无法证明成功，也无法证明新版软件本身有故障。它只是内部取证状态，**不是 OTA 结果**。

当新版已经启动但出现 `EVIDENCE_UNAVAILABLE` 时，主机保持在现有验收阶段（现有 HA 路径中即 U12/TARGET_ACCEPTANCE 或等价阶段），并执行一个**有界补验窗口**：

1. 保持当前可用业务服务，不为取得状态回执反复重启；
2. 使用限定次数的同源重试和至少一种独立等效证据补验；
3. 保留已验证的恢复点和自动回滚能力；
4. 阻止下一笔 OTA 和会破坏回滚条件的用户写入；
5. 补验得到 PASS，则提交新版，终态为 `SUCCESS`；
6. 补验得到 PROVEN_FAIL，则自动回滚；
7. 补验窗口结束仍无法取得 PASS，则**不再等待、不形成第三种结果**，本次 OTA 按“未能证明可安全提交”判定为失败路径并自动回滚；
8. 前代恢复并通过独立的最低健康合同后，持久化 OTA 终态 `FAILURE`。

因此，“无法证明新版成功”不会被描述成“新版软件已经证明损坏”，但对**本次 OTA 事务**而言仍然是失败，因为产品没有获得提交新版所必需的证据。

**状态接口不参与提交/回滚决策。** status 只能投影“当前事务阶段 + 最近一次验收证据 + 降级标志”。提交或回滚由宿主执行器读取持久验收证据决定。即使 status 完全不可用，宿主也必须独立收敛：新版在有界验收内通过则提交为 `SUCCESS`；否则自动恢复前代，前代健康后终态为 `FAILURE`。

升级阶段同样实行按阶段隔离的状态提供器。U1–U5 的准备信息、U6–U10 的恢复点/切换信息、U11–U12 的目标运行与业务验收信息不得相互成为必需依赖。一个旧阶段 provider 在当前阶段返回“不适用”或异常时，只能使相应附加字段降级，不能覆盖当前核心 phase。

对升级验收的核心约束可以概括为：

```text
CHECKER_FAILURE != TARGET_FAILURE
STATUS_API_FAILURE != TARGET_FAILURE
EVIDENCE_UNAVAILABLE != PROVEN_FAIL
OTA_TERMINAL_RESULT in {SUCCESS, FAILURE}
NO_ACCEPTANCE_PASS_AFTER_BOUND => OTA_FAILURE_AND_ROLLBACK
```

其中危险动作仍然 fail-closed：没有足够证据时不得提交新版。status/checker 单次异常不能立即触发破坏性回滚；必须先进入有界补验。但补验窗口结束仍无法取得提交证据时，本次 OTA 必须自动走失败回滚路径，不能无限等待，也不能要求普通用户决定。

## 6. 校验合同：什么证据能改变系统状态

每条**能阻止提交或触发恢复**的规则都要写清检查对象、适用时刻、正常证据、明确反例和取证失败的处置。检查器输出三类结果：**通过、已证实不满足、证据不足**。checker 只提供证据，不直接拥有事务推进、停服、回滚或恢复控制权；它自身抛错必须归类为“证据不足/观察链路异常”，不能伪装成“业务已证实失败”。按安装前记录的设备能力和配置选择适用项，例如从未启用历史记录的设备；不能把本次读取失败临时改为“不适用”。

| 检查对象和时刻 | 自动程序采用的证据 | 约束 |
| --- | --- | --- |
| 不变的发布包与旧镜像归档，释放内部空间之前 | 签名清单、平台、归档大小和完整摘要；旧镜像与实际前代的内容身份对应。导入后通过平台和兼容的镜像内容标识核对。 | 文件名、显示标签及单一 Docker 版本显示字段不足以证明镜像相同。 |
| 备份、恢复后的数据，应用仍静止时 | 写入方已退出且无其他写入者。按版本化清单核对受保护路径、必需元数据和内容摘要。对实际使用的数据库作一致性检查，包括恢复所需的伴随文件；回读加密归档并验证认证、解密和清单。恢复后、服务启动前复核。 | 明确定义临时文件及可再生缓存的排除范围。状态名、归档存在或解密命令退出成功，都不足以单独证明备份可用。 |
| 运行中的配置与历史 | 与升级前通过应用接口取得的基线比较。Manager 的节点身份及配对绑定仍可用；HA 挂载正确的数据目录，关键配置可读，能查询仍在保留期内的代表性历史。基线为空时验证读取正常、结果允许为空；时间窗选取须容许正常保留策略。 | 运行中的数据库、日志和时间戳会变化。此时不做全库字节相等、总行数相等或最新值必须改变的判断。样本查询只负责运行验收，完整备份另在静止时验证。 |
| 服务和业务链路，启动后 | Manager 能完成本地应用请求；Broker 的 TLS、既有授权连接和访问范围可用，动态安全配置及约定持久状态连续；HA 能完成应用请求并读取数据。对接收路径使用可关联的实际消息，或使用下述本地自检。组件版本与接受的组合一致。 | 容器 running、HTTP 端口打开、单条日志、单个客户端有流量都只能提供部分证据。温湿度恒定、零节点、节点离线或曲线断开，均不能单独判定升级失败。 |

**节点不在线时也要能验收主机。** 优先复用现有本机凭据、消息通道及 HA 接收能力。可关联的节点消息已经完整经过实际链路时直接采用。没有自然消息时，使用带本笔标识、无保留、无控制副作用的本机测试消息，在实际 Manager → Broker → HA 接收路径核对同一标识。使用受限测试位置，不写入农户的监测曲线，也不触发用户自动化。能证明本机收发即可完成主机验收，实际节点是否在线另行显示。若某一受支持部署无法安全实现等效检查，开发阶段先解决该部署的验收方法，再开放该发布；现场不能用“没节点”跳过接收检查。

### 6.1 各种结果对应的动作

- **准备期间。** 签名、摘要、恢复点或容量明确不满足时停止安装；读取异常也先保持旧版。两者分别记录原因，用户仍能使用原系统。
- **未提交，新版明确不可用。** 例如持续启动失败、确认加载错误镜像、已知应存在的历史在正确数据库中读不到，或本机通道可重复证实中断。排除启动未就绪及探针自身故障后，自动恢复旧版。
- **未提交，检查器异常。** 内部归类为 `EVIDENCE_UNAVAILABLE`，但这不是 OTA 结果。读不到记录、超时、未知格式或断言抛错时，先按同一事务换用已验证的独立取证方式并限定重试。必检事实在有界窗口内补齐则提交 `SUCCESS`；窗口结束仍无法取得提交所需证据，则本次 OTA 自动转失败回滚路径。旧版恢复并通过最低健康合同后，持久化 `FAILURE`。不得无限等待，不得要求用户选择“继续还是回滚”，也不得把未验证新版当成成功。
- **未提交，业务已中断。** 旧服务已停或新服务无法提供最低可用功能时，主机在局部观察期结束后接管，按第 5 节启动或恢复旧版。禁止把“工程检查报错”变成一个无人负责的停机终态。
- **回滚验收。** 旧版通过相同的业务合同才显示“已恢复旧版”。单项证据不足时保留已启动服务并补验。发布规则必须覆盖检查器故障和可预见的等效证据，普通用户没有“强制判定成功”的职责或按钮。

## 7. checker 的位置与升级

checker 是 `T1_Core_Updater` 内的校验模块。它接受对象和阶段，返回判定、证据来源和简明原因；启停、切换和恢复由事务执行器决定。三项业务组件维持原范围。**checker 不是恢复裁判，也不是恢复引擎的上游依赖。** checker 不可用、版本不匹配、规则异常或证据读取失败时，事务执行器按第 5.1 节处理：危险写动作保持 fail-closed，但已经成立的安全恢复责任继续执行。

- **规则可更新。** 发布清单提供目标版本、摘要、最低兼容版本等数据。校验逻辑变更随签名的宿主执行器更新包交付，记录规则版本。远端清单没有注入脚本或临时放宽规则的能力。
- **一笔事务固定一套规则。** 准备时绑定执行器和规则版本，安装、断电续办和回滚沿用。执行器只在没有活动事务时正常更新；切换前以既有正常、损坏和旧格式样本自检，保留能启动的前一版。若目标要求新版 checker，先完成执行器更新，再重新准备业务 OTA。
- **保留故障修复出口。** 极少数在途记录遇到旧 checker 缺陷时，允许经过签名和兼容性审核的修复程序对该事务重新读取既有事实，复用原恢复入口。持久记录原规则、修复版本与补验依据；禁止伪造成功、重放已消费授权或重新执行已完成的破坏性动作。操作由设备完成。
- **状态接口允许降级。** checker/status 无法取得非核心信息时返回缺失或降级标志，不得覆盖恢复引擎已经确定的核心 phase。checker/status 的故障记录与 `RECOVERY_ENGINE_FAILURE` 分开；只有恢复引擎依据核心事实失败时才能登记恢复失败。

优先复用宿主已有的可信软件包交付机制；若设备尚无此能力，则将执行器的签名交付列为开放相应版本 OTA 的前置实现项。第一版不引入 checker 专用容器、在线规则服务或第二套升级平台。

## 8. 面向农户的提示

安装前显示受影响功能、可能出现的数据缺口和用盘要求。例如：“安装期间，监测页面和依赖主机的告警可能暂停。请保持供电，看到‘可以拔出 U 盘’后再拔盘。” 用户只需决定是否开始安装，或在明确提示时插回原盘。

进度取自宿主机事务。可计量时显示“已备份 420 MB / 1.3 GB”等实际进度；未知总量时显示“正在恢复旧版”“正在启动监测服务”等步骤和最近一次有效进展，不显示虚构百分比。HA 或 Manager 停止时应能通过安装前提供的本地只读状态入口查看或重连；复用宿主的公开状态投影，仅返回脱敏字段，特权接口继续限于本机。分别显示**当前可用功能、所运行版本、升级结果、是否可拔盘**。可以出现“旧版已恢复，正在安全卸载 U 盘”。

## 9. 实施顺序和发布验收

优先补齐现有 HA 路径的两处责任：第一次停服即有主机接管；同一组数据在静止时与运行时各用正确证据。复用已有 U9+ 恢复协调、U13B 回滚、Generic V2 和产品接口。随后接入 Broker 与整套提交，最后从普通用户入口在备用 T1 上验证。既有 SOTA-R1 至 R7 可继续组织开发；产品不会在每个工程停点等待用户授权。

| 最少应覆盖的场景 | 通过标准 |
| --- | --- |
| 正常升级、重复点击、无变化组件、多组件中最后一项失败 | 同一请求只执行一次；只改所需组件；最后得到完整且可用的新组合或前代组合。 |
| 在第一次停服、内部旧镜像释放、恢复数据写入、服务启动和最终提交的前后分别中断 | 重启后自动核对实际状态，无重复删除或授权重放；提交前可恢复，提交后不覆盖新数据。 |
| 好备份遇到校验器异常；损坏备份面对工作正常的校验器 | 前者可以自动用等效证据复核，业务可用时不误停；后者在旧镜像释放前被拦截并恢复已停服务。 |
| 原盘内有其他文件和旧 OTA 目录、盘符变化、错盘、插回、空间临界及慢盘 | 其他文件和历史目录内容前后一致；错盘无写入，原盘自动续办；容量不足时保住旧版，慢速有进展时不误判死机。 |
| 带历史和配对的升级、数据结构迁移后回滚、空历史、节点离线、恒定读数与真实链路故障 | 同一发布分别证明正常数据可用、旧版数据恢复正确、真实故障能拦截、自然静默不会阻断验收。 |
| checker 版本变化、旧记录格式、业务已恢复但卸载或终态回执失败 | 在途事务规则稳定，旧记录兼容；状态与实际业务一致，收尾异常不触发重复回滚。 |
| status 接口异常、checker 抛错、Manager 断开、UI 无法刷新、附加容量/进度字段读取失败 | 恢复线程和升级执行器仍按持久事实运行；核心 phase 可继续返回或在接口完全失效时由宿主独立推进；不得加载未授权目标、不得重放授权、不得因为观察链路故障停止已恢复服务。 |
| 新版已启动但 status/checker 自身故障 | 保持 U12/等价验收阶段和恢复点；先有限重试和独立证据补验。PASS 才提交；明确失败立即回滚；补验到期仍无 PASS 也自动回滚。最终不得出现“待确认”终态。 |
| U10/U11/U12 等后置阶段误调用 U1–U5 状态提供器、未知 status 字段或新旧版本状态协议不一致 | 非适用附加字段降级为 UNKNOWN/缺失；核心恢复 phase 不被覆盖；协议兼容性失败只影响显示，不改变恢复事务。 |
| 用户关闭页面、更新期间断网、停机期间节点缓存溢出 | 设备独立完成安装或恢复；局域网恢复后能查看结果；曲线可有缺口，后续正常收数。 |

先用确定性模拟覆盖上述中断边界和正反样本，特别加入“状态接口失败但恢复正常”“恢复失败但状态接口正常”的成对故障注入；再在备用 T1 上从产品入口验证代表性成功、真实回滚和断电恢复。独立从 HA、业务接收、历史和 USB 文件取证，避免只让 checker 验证自己的输出。记录实际停机时长、数据量、介质及走过的恢复路径，用于改进。模拟通过、只读预检通过、源码审查通过和整机实测通过分别登记。

本版的交付标准是普通用户安装后能够继续使用监测系统。UI 的 OTA 最终结果只允许两种：**“升级成功”**，或**“升级失败，系统已自动恢复原版本”**。升级中、验证中和恢复中可以显示过程进度，但不能形成第三种最终结论。项目团队可以用同一套成功和失败样本重现这个结果。

## 10. V1.1.3 强制回归条件

V1.1.3 以后，以下条件属于产品级发布门槛，不再只作为单次缺陷修复测试：

- `STATUS_API_FAILURE != RECOVERY_ENGINE_FAILURE`。状态接口失败不得自动登记恢复失败。
- `STATUS_API_FAILURE != TARGET_FAILURE`，且 `CHECKER_FAILURE != TARGET_FAILURE`。状态/验收组件自身异常不得直接证明新版软件有故障。
- `EVIDENCE_UNAVAILABLE != PROVEN_FAIL`，但有界补验结束仍无 PASS 时，**本次 OTA 事务必须进入失败回滚路径**。
- OTA 持久终态字段只允许 `SUCCESS` 或 `FAILURE`；`PENDING`、`SAFE_HOLD`、`NEEDS_SUPPORT`、`EVIDENCE_UNAVAILABLE` 等均禁止作为 OTA 最终结果。
- 在 U9–U13 任一阶段故障注入 status/checker 异常，恢复线程仍能根据持久事务继续到等待介质、回滚或健康终态。
- 在 U11/U12 新版运行与验收阶段分别注入 status 超时、checker 抛错、错误阶段 provider、协议不兼容和附加字段读取失败；必须证明新版不会仅因观察器异常被错误回滚，也不会在证据不足时被错误提交。
- `RECOVERY_MEDIA_REQUIRED`、`ROLLING_BACK`、`ROLLED_BACK` 等核心状态在附加容量/进度信息不可得时仍可独立成立。
- Manager 停止、HA 停止、页面断开、UI 协议不兼容时，宿主恢复不依赖这些组件重新上线。
- 对未知核心事实不得继续向新版方向推进；必须证明没有目标镜像继续装载、没有进入下一破坏性阶段、没有授权重放、没有介质格式化，并自动选择最保守的前代恢复路径。
- 已恢复健康服务但观察链路仍异常时，维持服务并补验，不得为获得“漂亮的状态”反复重启或重复回滚。
- status 查询必须经过只读测试，证明查询本身不会改变事务摘要、服务状态、镜像集合、介质内容或授权状态。
